# 形象生成的任务查询与领取回执

本轮发现：头像任务的首次锁写入没有核实返回ID；部分历史、活动任务和候选列表查询把异常响应当作空数据。这些情况会削弱重复请求判断，不能继续据此提交付费任务。

## 修改与实测

`uniCloud-alipay/cloudfunctions/api_pet_avatar/index.js`增加了严格的查询和任务领取回执检查：

- 旧操作查询、当前任务、候选与恢复列表必须返回合法数组；服务错误、空元素、多条单文档结果均拒绝。
- 当前任务查询失败后不再降级寻找旧锁或假设没有任务。
- 首次领取必须有匹配的任务锁ID；替换和条件更新必须明确更新0或1条，多个兼容字段必须一致，不接受字符串计数。
- 历史查询异常不再触发候选重建或提供方轮询。会话候选列表和清理前列表读取异常也直接停止。
- 给客户端返回明确的“暂时无法确认生成记录”提示，保留原形象。

[修复前完整测试](avatar-database-before-2/tests.tap)：原有9项通过，新增6项失败。初次故障脚本因旧代码进入了等待中的模拟轮询而超时，保留在`avatar-database-before`；测试替身随后改成即时返回，以完整记录失败，未接触真实模型。

[实际生成入口测试](../../tests/rc-avatar-quota-integration.test.cjs)修复后15/15通过：异常查询和首次锁回执不明时提供方调用数为0；替换锁回执不明不追加调用；已受理任务的同操作重放、结果保存失败恢复、过时轮询与配额仍按原规则运行。

[local-13/results.json](local-13/results.json)：加入锁竞争和归属套件后，相关回归277/277通过。期间还执行了13项头像诊断脱敏、服务端身份与照片来源回执专项，均通过；它们不计入277项。

## 尚有限制

不确定的首次锁写入可能已经在数据库落为CREATING。本轮不会猜测性删除锁或盲目重新提交，所以该情况可能需要人工核对提供方流水后恢复；不能说“任何故障都能自动继续”。当前权益查询可能创建空账本，但此路径没有预留生成次数、没有提供方调用。

本轮没有重写所有头像数据库写入，也没有解决远端存储ACL、签名接口归属旁路或实际部署问题。修改仅在本地，所有模型、对象存储和数据库均为测试替身；没有新增真实图片费用，没有删除真实图片。
